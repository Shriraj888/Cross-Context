# Contributing to Cross Context

Thank you for your interest in contributing to **Cross Context**! This document outlines how to set up your local development environment, project conventions, testing workflows, and submission guidelines.

---

## 🛠️ Development Setup

Cross Context is built as a **zero-build, native ES-module Chrome Extension** targeting Manifest V3. You do not need Node.js or bundlers like Webpack/Vite to run or modify the core extension.

### 1. Prerequisites
- A Chromium-based browser (Google Chrome, Brave, Microsoft Edge, Arc, or Opera).
- Git.
- Optional: A code editor with modern JavaScript/HTML/CSS support (VS Code, Antigravity, Cursor, etc.).

### 2. Loading the Extension in Developer Mode
1. Clone the repository:
   ```bash
   git clone https://github.com/Shriraj888/Cross-Context.git
   cd Cross-Context
   ```
2. Open Chrome and navigate to:
   ```text
   chrome://extensions/
   ```
3. Enable **Developer mode** using the toggle switch in the top-right corner.
4. Click **Load unpacked** in the top-left corner.
5. Select the root `Cross-Context` directory (the folder containing `manifest.json`).
6. The extension is now loaded and ready for testing!

## 🏗️ Architecture & Code Organization

Cross Context strictly adheres to the Chrome Extension Manifest V3 security model:

```text
cross-context/
├── manifest.json              # Extension manifest (MV3 declarations & permissions)
├── background.js              # Service worker (messaging, storage, Gemini AI pipeline)
├── content/
│   └── content.js             # Content script (scrapers, injectors, preview overlay)
├── popup/
│   ├── popup.html             # Extension popup interface
│   ├── popup.css              # Obsidian & electric cyan design system
│   └── popup.js               # Popup event controllers & toast engine
├── utils/
│   ├── formatter.js           # Prompt formatting & message-boundary truncation
│   └── storage.js             # Async wrappers for chrome.runtime messaging
└── docs/                      # Technical documentation & deep dives
```

### Important Design Rules
1. **Single-File Content Script:** In Manifest V3, content scripts cannot use dynamic `import()`. As a result, all platform scrapers and injectors are unified in [`content/content.js`](file:///content/content.js).
2. **Decoupled Service Worker:** The popup UI never writes directly to `chrome.storage.local`. All persistence requests pass through [`background.js`](file:///background.js) via `chrome.runtime.sendMessage`. This ensures async operations (such as multi-pass AI distillation) survive popup closures.
3. **Vanilla Web Technologies:** Keep the bundle lightweight and dependency-free. Do not introduce npm packages or heavy runtime frameworks unless agreed upon in an RFC.

## 🧪 Testing Your Changes

When testing modifications:

### 1. Reloading the Extension
- Whenever you edit [`background.js`](file:///background.js) or [`manifest.json`](file:///manifest.json), click the **Reload icon (🔄)** on the extension card in `chrome://extensions/`.
- Content script changes in [`content/content.js`](file:///content/content.js) take effect upon refreshing the target LLM tab (`F5` or `Ctrl+R`).
- Popup changes in [`popup/`](file:///popup) take effect every time you reopen the extension popup.

### 2. Testing Platform Scrapers
Test scraping across supported target sites:
- [Claude.ai](https://claude.ai)
- [ChatGPT](https://chatgpt.com)
- [Gemini](https://gemini.google.com)
- [Grok](https://grok.com) & [X Grok](https://x.com/i/grok)
- [Perplexity](https://www.perplexity.ai)

Verify that:
- Formatting (fenced code blocks, bullet points, numbered lists) is preserved in extracted Markdown.
- UI elements (copy buttons, thumbs-up/down, share controls) are cleanly stripped.
- Message roles (`user` vs `assistant`) are correctly mapped.

### 3. Testing Injection
Verify that:
- Target input fields are populated without UI state clearance.
- Markdown file attachment (`context-con_01.md`) or fallback text pasting works reliably.
- Companion prompt text correctly references the generated Context ID.

## 🔍 Platform Selector Maintenance

Because AI platform interfaces evolve rapidly, scraping and injection selectors may require updates over time.

### Guidelines for Selector Updates
- Always prioritize resilient attributes:
  1. Semantic `data-*` attributes (e.g., `[data-message-author-role]`, `[data-testid]`)
  2. ARIA roles and semantic HTML tags (`article`, `main`, `[role="presentation"]`)
  3. Stable layout class patterns
- Never rely on single fragile CSS classes generated by CSS-in-JS compilers (e.g. `.css-19zrmue`).
- Add fallback selector tiers inside `resilientQueryAll()` rather than replacing working selectors.
- Update the documentation in [`docs/scraping-engine.md`](file:///docs/scraping-engine.md) when updating platform selectors.

## 📋 Pull Request & Branching Workflow

1. Fork the repo and create a feature branch:
   ```bash
   git checkout -b feature/amazing-feature
   # or
   git checkout -b fix/claude-selector-update
   ```
2. Keep commits atomic and use standard conventional commit prefixes:
   - `feat:` New feature or enhancement
   - `fix:` Bug fix or selector repair
   - `docs:` Documentation changes
   - `refactor:` Code cleanup without behavioral changes
   - `style:` Formatting or UI styling tweaks
3. Verify your changes don't cause console errors or memory leaks.
4. Submit a Pull Request with:
   - Clear description of the problem and solution.
   - Tested platforms and browser version.
   - Screenshots/GIFs for UI changes.

---

## 🛡️ Security & Privacy Guidelines

- **No Remote Dependencies:** Never load remote scripts via CDN or unverified third-party endpoints.
- **Strict Host Permissions:** Host permissions must remain strictly scoped to supported platform domains.
- **SSRF Prevention:** All proxy image-fetch routines must validate URLs using `isSafeImageUrl()`, rejecting non-HTTPS protocols, local hosts (`127.0.0.1`, `localhost`), and private IP ranges.

Thank you for helping keep Cross Context fast, reliable, and privacy-first!
